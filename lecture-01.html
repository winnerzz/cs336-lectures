CS336 学习台

第 1 讲 Overview and Tokenization

预计用时： 90-150 分钟

一句话： 语言模型只会处理一串整数，不认识文字。tokenizer 就是”文字 ↔︎ 整数”的翻译器，而 BPE 是怎样从数据里自动学出这张翻译表。它是全课第一个你要亲手写出来的部件，也直接决定序列有多长、训练有多贵。

学完你能：

  • 说清楚语言模型为什么必须先分词，以及 tokenizer 的好坏怎样牵动序列长度、显存和速度。
  • 区分”字符 / 字节 / 子词”三种切法各自的取舍，并解释为什么 len("世界")=2 而它的字节数是 6。
  • 手推一遍 BPE 的训练和编码，说明它凭什么能把序列压短。

前置知识：这一讲默认你已经会（我从 0 给你补）

CS336 默认你上过类似 CS224N 的入门课，所以不会重新解释下面这些。你基础偏弱，我先把这一讲真正用到的几块补上。更底层的 Python、字节、手写 BPE 实操，见 第 0 讲 · 基础搭建。

① 语言模型在干的唯一一件事：预测下一个词。 给一段已有文字，模型输出”下一个 token 最可能是什么”的概率。把这件事做准、做大，语法、事实、推理就会”顺带”被学会。整门课都是在教怎么把这件事做好——本讲负责它的入口：先把文字变成模型能吃的数字。

② 为什么必须是”数字”而不是”文字”。 模型内部全是矩阵乘法和加法，只能算数。所以任何文本进模型前，都要先翻译成一串整数（token id）；模型算完输出的也是数字，再翻译回文字给人看。这一进一出的翻译，就是 tokenizer 的活。

③ 字符、字节、编码的区别（本讲反复用）。 “字符”是人看到的一个字（世、a、😀）；“字节”是计算机真正存的 0–255 的数。.encode("utf-8") 把字符翻译成字节，一个汉字通常占 3 个字节。这块如果发懵，先去第 0 讲把脚本跑一遍再回来。

为什么课程从 tokenizer 开始

CS336 的主张是 understanding language models by building them from scratch——不满足于调 API，而是能讲清一个模型怎样被训出来、为什么这样训、资源限制怎样改变设计。第一个要动手的部件之所以是 tokenizer，是因为它不是普通的”文本预处理”，而是同时牵动三本账：

  • 它决定序列长度 → 序列越长，注意力计算越贵（算力账）。
  • 它决定词表大小 → 词表越大，嵌入矩阵越占显存（显存账）。
  • 它决定信息密度 → 同样一段文字切得好不好，直接影响模型每一步能学到多少（数据账）。

所以”怎么切词”这个看似琐碎的问题，是后面所有效率讨论的起点。

Tokenizer 是什么

语言模型处理的是整数序列，不是字符串。tokenizer 就是两者之间的双向映射：

encode(string: str) -> list[int]      # 文字 → 一串 token id
decode(indices: list[int]) -> str     # 一串 token id → 文字

也就是 text <-> token ids。一个合格的 tokenizer 只有两条硬要求：

  1. 可逆：decode(encode(text)) 要能还原原文，不能丢信息。
  2. 够紧凑：token 序列不能太长，否则 Transformer 的注意力开销会爆。

整门课关于 tokenizer 的所有取舍，本质都是在这两条之间找平衡。

三种最朴素的切法

方法 基本单位 优点 主要问题
字符级 (Character) Unicode 码点 概念最简单 Unicode 范围极大；人眼的”一个字”和码点不总一致
字节级 (Byte) UTF-8 字节 词表固定 256，任何文本都能表示 序列很长，压缩率低
词级 (Word) 单词 / 正则切片 token 自带语义 词表巨大；没见过的新词无法处理

字符 ≠ 字节（一个必须亲眼看到的例子）

len("世界")                  # = 2   ← 数的是"字符个数"
len("世界".encode("utf-8"))  # = 6   ← 数的是"字节个数"

一个汉字在 UTF-8 里要用 3 个字节表示，两个字就是 6 个字节。字节级 tokenizer 的词表因此永远只要 256 个编号（0–255），天然能表示任何语言、任何符号——代价是序列被拉得很长。三种朴素切法各有死穴，这就引出了折中方案：BPE。

BPE：让数据自己决定词表

核心思想（骨）：从字节开始，反复把”语料里出现最多的相邻一对”合并成一个新符号。 常见组合被压成单个 token，序列自然变短；而词表不是人工规定的，是从数据里学出来的。它兼顾两条硬要求：底层是字节（任何文本都能编码、可逆），上层学出的合并规则（把常见片段压短）。

下面把它拆到”能亲手复现”的程度。

训练：手算一遍 the cat in the hat

为看得清，下面在字符层面演示（ASCII 字符就等于它的字节，逻辑和字节级完全一样；␣ 表示空格）。初始序列：

t h e ␣ c a t ␣ i n ␣ t h e ␣ h a t

第 1 轮——数所有相邻对的出现次数（只列 ≥2 的）：

(t,h)=2   (h,e)=2   (e,␣)=2   (a,t)=2     其余都是 1

出现 2 次的有好几对，平手时按一个固定规则定胜负（实现里通常按 pair 的字典序，保证结果可复现）。取 (t,h)，分配新 id 256，把序列里所有 t h 替换掉：

[256] e ␣ c a t ␣ i n ␣ [256] e ␣ h a t      # 256 = "th"

第 2 轮——在新序列上重新数：(256,e)=2、(a,t)=2…取 (256,e) → id 257 = "the"：

[257] ␣ c a t ␣ i n ␣ [257] ␣ h a t          # 257 = "the"

第 3 轮——(a,t)=2（来自 cat、hat）最高 → id 258 = "at"：

[257] ␣ c [258] ␣ i n ␣ [257] ␣ h [258]      # 258 = "at"

3 次合并后，序列从 18 个 token 缩到 13 个，并且学到了一张合并表（merges），按学习顺序排好：

rank 0:  (t, h)   -> 256
rank 1:  (256, e) -> 257
rank 2:  (a, t)   -> 258

关键直觉：合并是有先后顺序的，257 是建立在 256 之上的（“the” = “th”+“e”）。这个顺序在编码时至关重要——见下。

编码：为什么必须”按学习顺序”套合并

训练得到 merges 后，给一段新文本编码，不是随便合并，而是严格按 rank 从小到大、反复套用。例：编码 that：

t h a t
→ 套 rank0 (t,h)->256 :  [256] a t
→ 套 rank1 (256,e)->257:  无 (256,e)，跳过
→ 套 rank2 (a,t)->258 :  [256] [258]
结果: [256, 258]

为什么必须按顺序？因为高阶 token 依赖低阶（257 需要先有 256）。乱序合并会得到和训练时不一致的切分，破坏可逆性与压缩率。这是 BPE 实现最容易写错的地方。

最终词表怎么构成

一个字节级 BPE tokenizer 的词表 = 三部分拼起来：

[0 .. 255]            256 个原始字节（保证任何文本都能表示、可逆）
[256 .. 256+M-1]      M 个学到的 merge（高频片段）
[再往后]              special tokens（如 <|endoftext|>，见下）

目标词表大小（如 GPT-2 的 50257）减去 256 和 special token 数，就是要学的 merge 次数 M。

数据结构与复杂度（接 L02 的工程脑）

  • 数 pair 用 dict：{(a,b): 次数}，查一对几乎一步到位；用 list 从头找会慢死。
  • 朴素训练的代价：每合并一次就把整个语料重扫一遍来重新计数 → 约 O(N × M)（N 语料长度、M 合并次数）。语料上万亿时这是天文数字，所以真实实现会增量更新计数（一次合并只影响被合并位置附近的几对），而不是每轮全扫。
  • 这正是第 0 讲”估执行次数”的实战，也是 L02 资源会计 mindset 的起点。

两个绕不开的工程细节

pre-tokenization：先粗切，再让 BPE 在词内部合并

如果直接对整段文本跑 BPE，它会把空格、标点也卷进合并，学出 "the."、"in the" 这种跨词的垃圾 token，还让不同上下文里的同一个词被切得不一样。

做法：先用一个正则把文本粗切成”词 / 空格 / 标点”小块（chunk），BPE 只在每个 chunk 内部合并、绝不跨 chunk。 GPT-2 的那条正则就是干这个的（把 's、前导空格、连续字母、连续数字、标点各自分开）。好处有二：① 切分更规整、语义更稳；② 各 chunk 独立 → 计数可并行、可去重加速。A1 要求你实现它。

special tokens：必须整体保留，不能被拆

像 <|endoftext|> 这种标记，含义是”文档边界”，绝不能被 BPE 当普通文本拆开。做法：给它们保留专门的 id，编码前先按 special token 把文本切开，特殊段直接映射到它的 id，其余段才走正常 BPE。这样它永远是一个完整 token。

动手练习

练习 1：写出接口。 默写 encode / decode 两个函数签名，并用自己的话说出各自的输入、输出是什么。

练习 2：解释字节长度。 解释为什么 len("世界")=2 而 len("世界".encode("utf-8"))=6，要点出”字符个数”和”字节个数”的区别。

练习 3：手工训练 BPE。 对 the cat in the hat 做 3 次 merge，每次写出：最高频 pair、分配的新 id、合并后的序列，并最终列出 merges 表（带 rank）。对照正文的 trace 自查。

练习 4：手工编码（考合并顺序）。 用练习 3 得到的 merges 表，把新词 theft 编码成 id 序列——按 rank 从小到大套合并，写出每一步。（提示：先 th→256，再看有没有 (256,e)……）

练习 5：想复杂度。 朴素训练每合并一次就全语料重扫计数，约 O(N×M)。说说为什么语料一大就不可行，以及”只更新被合并位置附近的计数”为什么能省。
