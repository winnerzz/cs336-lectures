计算机基础：机器只会对数字做加减乘

计算机没有”理解”。它能做的只有一件事：把一堆数字搬来搬去，做加减乘。所谓”训练一个语言模型”，拆到底就是对几十亿个数字反复做加减乘。先把”数字怎么存、怎么搬”搞清楚，CS336 后面讲的显存、带宽、精度才有根。

一切都是数字：bit 与 byte

  • bit（位）：计算机里最小的单位，只有 0 或 1 两个状态（一个开关）。
  • byte（字节）：8 个 bit 绑在一起，能表示 2^8 = 256 种状态，也就是 0–255 这 256 个整数。
  • 文字、图片、模型参数，存进计算机时全都先变成一串字节。

这就解释了第一讲一个关键事实：一个字节级 tokenizer 的词表正好是 256——因为一个字节只能是 0–255。文字怎么变成字节，下面”脚本 1”会让你亲眼看到（中文一个字占 3 个字节，所以 len("世界")=2 但它的字节数是 6）。

整数和小数怎么存（后面 L02 会用到）

  • 整数很直接：用若干 bit 按二进制记下来。
  • 小数（浮点数）麻烦些：用固定的 bit 数，一部分记”大概多大”（范围/指数），一部分记”小数有多准”（精度）。bit 给得越多越精确，但越占地方。

这就是 L02 里 fp32 / bf16 的来历：fp32 用 4 字节存一个数（准但费显存），bf16 用 2 字节（省一半显存，训练首选）。你现在只需记住一句：“一个数占几个字节”是可以选的，省字节 = 省显存，但要付出精度代价。

数据放哪：内存、硬盘、显存

同样是”存数字”，存的地方不一样，速度差几个数量级：

地方 比喻 特点
硬盘 / SSD 仓库 最大、最慢、断电不丢
内存 (RAM) 工作台 快、断电就没、CPU 直接用
显存 (GPU memory) GPU 的专属工作台 GPU 计算时数据必须先放这；容量小、最贵

自学者最常撞的墙就是显存不够（模型放不进 GPU）。L02 教你算”一个模型要多少显存”，L05 讲 GPU 为什么这么设计。先记住层次：越快的存储越小越贵。

为什么”算得快”还不够：搬数据才是瓶颈

直觉上你以为程序慢是因为”算得慢”。其实现代硬件算得飞快，常常是在等数据搬过来。做一次计算分三步：① 从内存把数据搬到计算核心 → ② 算 → ③ 把结果搬回去。如果第①③步（搬运）比第②步（计算）还久，核心就在空等。

这是贯穿 CS336 的核心洞见，L02 叫它 arithmetic intensity / roofline：一个操作是被”算力”卡住还是被”带宽（搬运速度）“卡住。很多优化（L03 的 RMSNorm、L06 的 FlashAttention）提速的真正原因都是少搬数据，而不是少算。现在记住这句就够：省时间往往靠少搬数据。

算法思维：怎么从 0 想出一个算法

很多人卡在”我知道要干嘛，但不知道代码怎么下手”。其实从 0 想算法是有套路的，不靠灵感。这一节给你一套可复用的方法，然后用它把 BPE 现场推一遍。

先说清楚：算法到底是什么

算法 = 一串确定的、能机械执行的步骤，把输入变成想要的输出。 关键词是”机械执行”——每一步都明确到”不用动脑、照做就行”。菜谱、长除法、查字典，都是算法。写代码之前，你要先在脑子/纸上把这串步骤想清楚，代码只是把步骤翻译给机器。

五步法：从模糊问题到能跑的代码

遇到任何”该怎么写”的问题，按这五步走，基本不会卡：

  1. 说清输入和输出。 把问题逼成一句话：“给我 ____（输入），我要得到 ____（输出）。” 说不清就还没想明白。
  2. 手做一个最小例子。 先别碰代码。拿一个很小的例子，用纸笔自己算一遍，得到正确答案。
  3. 观察：我在重复做什么？ 看你手算时那些”又做了一遍”的动作——那就是要写成循环的部分；那些”要记住的中间结果”——那就是要存进变量/字典的东西。
  4. 写成步骤（伪代码）。 用大白话把过程列成编号步骤，每步都机械可执行。先不管语法。
  5. 翻译成代码 + 用第 2 步的小例子验证。 把伪代码翻成 Python，跑一遍，看输出是不是等于你手算的答案。不对就回到出错的那一步改。

写不出来时，99% 是卡在第 1、2 步——问题没说清、或者没自己手做过例子。先退回去手做。

用五步法走一遍 BPE

脚本 2 的 BPE 不是凭空写出来的，正是这么推出来的：

  1. 输入输出：给一段文字，输出”把最常见的相邻组合压成新符号后”的更短序列 + 学到的合并规则。
  2. 手做最小例子：拿 the cat in the hat，纸上数一遍哪两个字符挨在一起最多。
  3. 观察重复：“数每一对出现几次”→ 要循环；“哪一对最多要记下来”→ 要个字典；“合并完再来一遍”→ 外层还要循环。
  4. 伪代码：① 文字转字节；② 数所有相邻对的次数；③ 找最多的一对；④ 给它一个新编号、全部替换；⑤ 重复 ②–④ 若干次。
  5. 翻译+验证：写成代码，跑 the cat in the hat，看 th、the 这些是不是真的被压成了单个符号。

这五步就是脚本 2 的结构。读脚本时对照着看，你会发现”原来算法是这么一步步逼出来的”，而不是天才拍脑袋。

复杂度直觉：为什么朴素写法在大数据上会爆

同一个问题有多种写法，在大数据上快慢可能差几千倍。不用学严格的数学，先建立一个直觉：估一下”你的步骤会被执行多少次”。

  • BPE 里”数所有相邻对”：序列长 N，数一轮要看 N 次；要合并 K 次就重来 K 轮 → 大约 N × K 次操作。
  • N（语料）动辄上万亿、K（词表）几万——N × K 就是天文数字。慢一点点 × 巨大规模 = 多跑好几天、多烧几十万美元。

所以 CS336 处处在”省”：第一讲的 pre-tokenization（先粗切再合并，减少无谓的对）、L02 的整套”算账”思维，都是因为规模一大，“够不够聪明地写”直接决定花多少钱。想算法时，顺手想一句”它在大规模下贵不贵”，就是 CS336 要培养的工程脑。

三个够用的数据结构：list、dict，以及为什么 dict 快

数据结构 = “数字放在什么样的容器里”。这门课入门只需三个直觉：

  • list（列表）：一排按顺序排好的东西，[10, 20, 30]。token 序列就是一个 list。
  • dict（字典）：一张”查询表”，key → value，比如”某一对字符 → 它出现的次数”。
  • 为什么 dict 查得快：在 list 里找一个东西，可能要从头翻到尾（N 次）；dict 用”哈希”几乎一步就定位到。BPE 要反复”查某一对出现几次”，用 dict 才不会慢死——这正是上面”估执行次数”的实战。

选对容器，往往就决定了算法快不快。这也是为什么脚本 2 用 dict 来数相邻对。

脚本 2：从空白手写 BPE（5 步）

跑 02_bpe_from_scratch.py，它把上面”五步法”推出的 BPE 拆成 5 个能看到结果的小步：

  1. 把文字 encode 成一串整数（字节）。
  2. 用字典数每个”相邻对”出现几次。
  3. 用 max 找出现最多的那一对（比如 th）。
  4. 把这一对替换成一个新 id（从 256 开始，因为 0–255 被原始字节占了）。
  5. 把前几步放进循环 = 训练；再用学到的规则给新文本编码。

运行后你会看到 "the hat" 被编码成 [258, 104, 259]，其中 258 = 'the '、259 = 'at'——常见组合被压成单个 token，这就是 BPE 的压缩效果，也是第一讲和 A1 的核心。
